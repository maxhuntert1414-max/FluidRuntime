# FluidRuntime v0.10.0 Readback Elision Evidence

## Result

FluidRuntime can now interfere with a repeated D3D11 readback path inside the
owned cooperative target. A dedicated managed policy authorizes only redundant
whole-resource copies from an observed `D3D11_USAGE_DEFAULT` resource to an
observed `D3D11_USAGE_STAGING` resource with `D3D11_CPU_ACCESS_READ`.

Each run uses a 4 MiB source, one required copy/map, and 64 unchanged
copy/map repetitions:

| Run | Readback copies observed | Read maps | Copies forwarded | Readback copies skipped |
| --- | ---: | ---: | ---: | ---: |
| Baseline | 65 | 65 | 65 | 0 |
| Optimized | 65 | 65 | 1 | 64 |

The optimized path avoids 268,435,456 logical copy bytes per run. It still
performs all 65 CPU read maps and compares all 4 MiB after every map.

## Safety Contract

- Control action 2 is distinct from generic copy-elision action 1.
- Source and destination usage/access classes must have trusted creation and
  lifetime provenance.
- The policy is one process-local epoch, expires within four seconds, and has
  an exact 64-action budget.
- Every copy, map, skip, byte estimate, policy transition, and lifecycle event
  must agree between the native snapshot and managed ABI 7 ring.
- Every raw run requires zero lost sequences and zero native overruns.
- First-map, final-map, expected, source, and post-detach destination FNV-1a
  hashes must be identical.
- Detach must restore original dispatch before the final content check.

## Verification

- Managed tests: 68/68 passed.
- Native CTests: 7/7 Release and 7/7 Debug passed.
- Negative control-policy matrix: 320/320 processes passed across WARP Release
  and Debug.
- WARP readback trace: 4/4 raw runs passed; performance claim blocked because
  it used a software adapter and only two pairs.
- AMD trace: 22/22 raw runs passed with 1 warmup pair and 10 measured pairs.

## AMD Radeon RX 580 2048SP

Adapter vendor/device: `0x1002 / 0x6FDF`. All ten measured pairs favored the
optimized run for both CPU QPC duration and the guarded GPU timestamp interval.

| Metric | Baseline p50 | Optimized p50 | Baseline p95 | Optimized p95 |
| --- | ---: | ---: | ---: | ---: |
| CPU workload | 544,800.350 us | 421,077.150 us | 575,244.930 us | 442,802.645 us |
| GPU timestamp interval | 528,879.480 us | 406,132.160 us | 558,646.270 us | 427,418.994 us |

Paired p50 deltas were -107,946.350 us for CPU and -105,755.500 us for the GPU
timestamp interval. Paired p95 deltas were -66,608.060 us and -65,655.064 us.
The v0.10 performance gate passed for exactly:

`owned-d3d11-default-to-staging-readback-workload-only`

The GPU timestamp interval is elapsed work between D3D11 timestamp commands;
it is not a hardware-counter measurement of GPU busy time and can include idle
time while later commands are submitted. The paired workload and order are
controlled, but this distinction remains part of the claim boundary.

## Non-Claims

This release does not prove physical VRAM placement, PCIe traffic reduction,
RAM/VRAM residency control, upload (`RAM -> GPU`) optimization, external-game
support, FPS improvement, power reduction, D3D12/Vulkan support, or a general
readback cache. Resource placement and transfer details remain controlled by
Windows, WDDM, the D3D11 runtime, and the display driver.
