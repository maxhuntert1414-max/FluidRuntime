# FluidGateway-Managed Update Upload Evidence v0.15.0

Recorded on 2026-08-01 between FluidRuntime 0.15.0 and FluidGateway 0.64.0.

## Scope

This milestone closes one deliberately narrow control loop. FluidGateway makes
live FluidLink v2 decisions for repeated RAM-to-VRAM-intent uploads. FluidRuntime
accepts only an exact set of 64 `deduplicate-identical-transfer` decisions and
maps that authorization to native D3D11 action bit 8 with budget 64. The owned
hook remains the final authority: matching destination generation and an exact
4 MiB `memcmp` are required before each `UpdateSubresource` call can be skipped.

This proves functional Gateway-to-hook actuation in an owned cooperative
workload. It does not prove game FPS, external-process safety, physical PCIe or
RAM/VRAM traffic reduction, residency control, power savings, or a production
per-frame scheduler.

## Control Contract

Each optimized run performs 74 loopback round trips: Hello, heartbeat, session
and frame lifecycle, two resource registrations, one required seed upload, 64
candidate uploads, lifecycle endings, and Goodbye. The bridge requires:

- exact FluidLink v2 contract SHA-256;
- an exact IPv4 loopback TCP tuple owned by the caller-supplied expected
  Gateway PID, with its executable SHA-256 and process start time verified;
- advertised server name `fluidgateway` and the required capability mask;
- correlated wire and runtime session identities;
- one executed seed upload;
- 64 accepted opcode-2 decisions with `executed=false`;
- native action mask 8, budget 64, and expiration no longer than four seconds;
- matching owned target PID and shared-memory ring PID.

Before the first authorization, Runtime opens the target executable and hook
DLL with write/delete sharing denied, hashes those handles, and keeps them open
through all runs. Before publishing a policy, the launched main module and
loaded hook module must match those frozen paths and hashes. A unique context
SHA-256 binds nonce, peer PID/hash/start time, target/hook hashes, pair/phase,
resource size/count, action mask, and budget; that digest is carried in the
Runtime session and every candidate operation.

This is OS-verified binding to an expected local process, not cryptographic
peer authentication. The report records
`peer_cryptographically_authenticated=false`; it does not defend against a
compromised expected process or establish a remote trust channel.

Gateway decisions authorize only candidate attempts. They are not content
proof. Native generation invalidation, exact comparison, one-resource/4 MiB
cache limits, action reservation, content equivalence, and rollback remain
mandatory.

## Failure Contract

The integration harness also runs three adversarial control peers before any
optimized target is launched:

1. a TCP peer that returns a malformed FluidLink frame;
2. a TCP peer that accepts the connection and withholds every response;
3. a valid FluidLink peer that delays each response by only 100 ms.

One linked deadline covers connect, OS peer verification, and all 74 RTTs. The
third control proves that individually short waits cannot accumulate into an
unbounded authorization: it completed two RTTs before the 500 ms total deadline.
All three cases return CLI exit code 3, launch a fresh unmodified baseline process,
forward all 70 native `UpdateSubresource` calls, skip zero, publish no epoch,
mask, budget, or expiration, preserve content, and restore the hook. The
recorded failure types are `FluidLinkV2ProtocolException` and `TimeoutException`,
with elapsed time, deadline, and completed-RTT progress in each failure trace.

## Hardware Method

- adapter: AMD Radeon RX 580 2048SP;
- vendor/device: `0x1002` / `0x6fdf`;
- adapter LUID: `000000000000e28d`;
- one warmup pair plus ten measured alternating baseline/optimized pairs;
- target SHA-256:
  `cb05cff3b792f373147f1607317d70d93284eca3fcd210e0147bd33add7115e4`;
- hook SHA-256:
  `f3cbc3c27c111f03b2d294a506905e758de33dad29d04c3453b0c8905bc2123e`.

All 22 raw hardware runs preserved adapter identity, event continuity, exact
content, mutation and generation guards, policy accounting, and rollback. Each
optimized run skipped exactly 64 repeated 4 MiB updates, representing
268,435,456 logical bytes not submitted through those API calls.

## Result

| Native workload interval | Baseline p50 | Optimized p50 | Baseline p95 | Optimized p95 |
| --- | ---: | ---: | ---: | ---: |
| CPU QPC | 325,056.300 us | 90,240.900 us | 349,183.625 us | 114,324.165 us |
| GPU timestamp | 274,956.460 us | 3,504.400 us | 296,985.492 us | 4,116.120 us |

Optimized won 10/10 measured pairs in both intervals. Paired CPU delta-percent
p50/p95 was -71.857% / -65.326%; GPU was -98.764% / -98.463%.

The 11 authorization sessions performed 814 FluidLink round trips, sent
234,135 frame bytes, and received 60,181. Authorization latency was 34,643 us
p50 and 94,087 us p95. Authorization occurs before optimized target launch and
outside the native timing interval, so the closed-loop report always sets
`performance_claim_allowed=false` with blocker
`gateway-authorization-outside-native-timing-window`. The native numbers above
describe only the controlled workload after authorization.

```powershell
dotnet build FluidRuntime.slnx -c Release
cmake -S native -B native/build -A x64
cmake --build native/build --config Release

powershell -NoProfile -ExecutionPolicy Bypass `
  -File tools/Test-GatewayManagedUpdateUpload.ps1 `
  -GatewayPath ..\FluidGateway `
  -TrialPairs 10 `
  -WarmupPairs 1 `
  -Hardware $true
```
