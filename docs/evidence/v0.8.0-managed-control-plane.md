# v0.8.0 Managed Control-Plane Evidence

Captured on 2026-07-15 with the final v0.8.0 implementation. This release is
the first FluidRuntime slice in which the managed runtime publishes a bounded
policy and the native hook applies it. The proof remains limited to the owned
D3D11 target and one already-proven redundant `CopyResource` call.

## Contract

- Snapshot ABI v9, attach-options ABI v2, ring ABI v6, and control ABI v1 are
  versioned together.
- The shared mapping contains a 64-byte event header, a 64-byte control block,
  and 1,024 fixed 80-byte events.
- The target must opt in with `fluid_hook_attach_flag_allow_control_policy`.
- The manager publishes epoch 1, the single supported action bit, a budget of
  one action, and an expiration no more than four seconds in the future.
- The native hook accepts only that exact epoch, action, budget, and lifetime,
  caches the accepted policy, emits `ControlPolicyAccepted`, and acknowledges
  the epoch. Invalid policies fail closed.
- Managed-policy hook entries are serialized while the authority is active, so
  provenance proof and action commit cannot be crossed by another tracked hook
  operation. Expiration is checked again after budget reservation.
- `CopyResource` consumes the budget only after the existing owned-resource
  generation model classifies the call as redundant and estimates non-zero
  bytes. There is no managed round trip on the API call.
- The optimized run must finish with one applied action and status `exhausted`.
- Baseline and optimized processes must agree on adapter identity, event and
  snapshot accounting, resource lifecycle, subresource hashes, exact readback,
  restored API dispatch, and disabled actuation after detach.
- Original vtable entries are restored at detach, while the module remains
  pinned until the owned target exits to keep delayed function pointers valid.
- Retained entrypoints are pure forwarding while detached: they do not mutate
  metrics, events, or provenance. A second attach is rejected because this ABI
  has no attachment generation with which to isolate delayed calls or readers.

The report exposes four control lanes. Copy-path actuation is
`active-owned-lab`; CPU scheduling and RAM/VRAM residency are
`blocked-no-native-backend`; presentation remains `observe-only`.

## WARP Run

- Adapter: Microsoft Basic Render Driver
- Trial design: 2 measured pairs, no warmup
- Native/managed runs: 4
- GPU timing valid: 2/2 measured pairs
- IPC events: 1,503, with no sequence loss or native overrun
- Accepted/exhausted policies: 2/2 optimized runs
- Avoided per optimized run: 1 call / 4,096 bytes
- Exact content equivalence and rollback: 4/4 runs
- CPU paired delta: p50 `-0.7 us`, p95 `+16.22 us`
- GPU paired delta: p50 `+4.65 us`, p95 `+100.905 us`

The performance gate was blocked because two measured pairs are insufficient
and only 1/2 GPU pairs favored the optimized run. This trace is correctness
evidence, not a WARP performance claim.

## AMD Hardware Run

- Adapter: AMD Radeon RX 580 2048SP (`1002:6FDF`)
- Trial design: 1 excluded warmup pair and 10 measured pairs
- Native/managed runs: 22
- GPU timing valid: 10/10 measured pairs
- IPC events: 7,648, with no sequence loss or native overrun
- Accepted/exhausted policies: 11/11 optimized runs
- Avoided per optimized run: 1 call / 4,096 bytes
- Exact content equivalence and rollback: 22/22 runs

The positive-performance gate was **blocked**. GPU paired delta was p50
`+43.2 us` and p95 `+46.176 us`; only 1/10 pairs favored the optimized run.
CPU paired delta was p50 `+182.9 us` and p95 `+1141.035 us`; 3/10 pairs favored
the optimized run. The optimized workload was slower, but this trace does not
identify the internal cause. It proves controlled actuation and fail-closed
evidence handling, not an efficiency win.

## Detach and Stale-Call Stress

The final Release binary completed 123 concurrent create/destroy cycles before
detach. Captured stale `CreateBuffer` and `Release` entrypoints forwarded after
detach without changing the native snapshot. A second attach failed closed with
`ERROR_ALREADY_EXISTS`; a second detach returned `S_FALSE`. Original dispatch,
zero Release/provenance failures, and rollback were all confirmed. The same
contract also passed 100/100 repeated local executions.

Report: [concurrent-stale-forwarding-warp-v0.8.0.json](traces/concurrent-stale-forwarding-warp-v0.8.0.json)

## Reproduction

```powershell
dotnet run --project src/FluidRuntime -c Release -- manager-lab `
  --target native/build/Release/fluidruntime-hook-target.exe `
  --hook native/build/Release/fluidruntime-present-hook.dll `
  --frames 120 --hold-ms 250 --gpu-timeout-ms 1000 `
  --trial-pairs 10 --warmup-pairs 1 --hardware true `
  --out artifacts/manager-control.json

native/build/Release/fluidruntime-hook-target.exe `
  --hook native/build/Release/fluidruntime-present-hook.dll `
  --concurrent-lifetime-stress `
  --out artifacts/concurrent-stale-forwarding.json
```

This evidence does not prove external-process safety, game compatibility,
automatic FPS gains, CPU scheduling control, RAM/VRAM residency control,
regional-copy elision, or Apple-Silicon-like physical memory behavior.
